# Agent Note: Bounded audio allocation

Status: implemented

## Problem

原解码器每次把完整 BLE 包拼到 `pendingBytes`，解码后移除前缀，但保留较大的容量到后续会话。播放回调只需要样本数量，却因访问 `samples.count` 延长原始 PCM 数组的生命周期。逐包回环解析还重复构造全部设备的显示数组。

## Decision

解码器直接读取 Data 的完整帧，只缓存不足一帧的剩余字节。完成播放回调只捕获整数计数，原始数组在提交 AVAudioPCMBuffer 后可以释放。回环解析仅枚举一次并检查指定 UID 的存活、双向通道和名称；设备列表与就绪状态相同时不重复发布 UI 更新。

不改变 IMA/DVI 算法、4096 字节包上限、32000 样本队列、尾音排空、支持设备或默认输入策略。不引入额外音频池、驱动或依赖。

## Alternatives considered

- 缩小音频队列以降低内存：会降低对延迟的容忍，未采用。
- 永久复用所有音频缓冲：需要跨实时回调协调资源，增加取消和排空风险，当前优先解除无意义保留。
- 只报告整个应用 RSS：受 SwiftUI、系统缓存和硬件状态影响，不能精确说明这次局部优化，因此测量可复现的缓存容量并说明范围。

## Consequences

相同 CLT 优化构建、120 字节帧及 4096 字节合成包，原残余缓存容量 5088 字节，现为 16 字节，reset 后也分别为 5088/16；输出样本数 8160、摘要、predictor 和 index 一致。这不代表整个应用内存减少同等比例，长期不同分片的残余容量会随不足一帧的内容调整。

新增分片一致性和超大包不改状态检查；核心 69/69、适配器 59/59、CLT build、bundle、文档及脱敏检查通过。真实输入目录只读检查移除了 18 个 listener、系统默认设备未变；未读取或播放真实语音。
