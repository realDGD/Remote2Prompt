# Agent Note: 无证书源码构建的固定升级身份

Status: implemented

## Problem

0.2.12到0.2.13的普通Homebrew升级保留了配置，但macOS的TCC日志明确记录输入监控和设备控制的旧代码要求无法匹配新代码哈希。源码编译、严格签名有效和设置保留不能证明系统授权在更新后仍有效。

## Decision

用户明确选择尝试无证书的固定身份规则。0.2.14开发源码的Homebrew构建采用显式`identifier "dev.remote2prompt.app"`，不绑定每次变化的代码哈希。初次打包和写入来源信息后的最终签名共用`scripts/sign-app.sh`，并检查实际指定要求而不只检查签名完整性。本地普通构建继续默认哈希身份，显式开启固定模式才使用新规则。

`HomebrewSource.plist`声明`identifier-only-adhoc-v1`策略，构建和安装核验检查声明与最终身份一致；旧版缺少声明时明确报告旧版检查。公开Cask与安装版仍为0.2.13，尚未采用此规则；真实TCC授权跨更新持久性尚未验证，不把离线代码要求检查写成授权成功。

## Alternatives considered

- 继续默认ad-hoc代码哈希：无需证书，但代码变化会使现有哈希要求不再匹配；本机已出现实际失配。
- 本机持久签名证书：可约束签名者，但用户本轮明确不创建证书或私钥。
- Developer ID签名公证成品：适合公开二进制分发，但改变用户机器上CLT源码编译的安装要求。
- 自动改写TCC、清隔离标记或关闭Gatekeeper：不采用；签名身份、系统授权和首次启动信任独立处理。

## Consequences

两个不同代码哈希的副本，在写入来源信息并最终签名后，均满足同一显式身份要求；其他应用标识及签名内容损坏被拒绝。实际检查与尚未覆盖的系统验收见[记录](../../../../docs/validation/2026-10-29-certificate-free-identity.md)。

迁移时仍需用户重新关联一次授权，再经真实远端源码升级，直接读取系统权限状态和TCC记录确认保留；这项尚未执行。不创建证书、不改钥匙串，不把发布、安装或系统授权视为源码修改的隐含步骤。

固定规则仅校验应用标识，不验证开发者或签名证书；其他程序也能声明相同标识。源码归档SHA-256和完整性签名不能替代发布者身份约束。此规则不提供Developer ID、公证或Gatekeeper批准；不同macOS版本下的TCC接受行为仍需实测。
