# 无证书固定身份的源码构建试验

日期：2026-10-29。用户要求先核实普通升级是否失去权限，随后明确选择尝试无证书的固定身份规则。只修改本项目构建与验证，不重置TCC、清隔离标记、创建证书或修改系统安全设置。

## 已确认的故障

本机Homebrew日志记录0.2.12到0.2.13的普通升级，配置数据及向导标记在新应用首次启动前保持一致。紧接升级后的TCC系统日志对输入监控及设备控制明确报告`Failed to match existing code requirement`，旧、新代码哈希不同。后续系统记录已更新为新版授权，原生权限页也显示允许；这不否定升级时的实际失配。

Homebrew的`signer changed`提示属于启动隔离批准继承逻辑，本身不能证明TCC授权失效。本次故障结论依据实际TCC日志，原始诊断只保留在忽略目录，不上传。

## 第一阶段：统一签名入口

`build-app.sh`使用统一的`sign-app.sh`，保留本地默认代码哈希与显式固定身份两种模式；已有证书入口保持可用，不创建证书。`verify-signing-identity.sh`同时检查严格签名有效性和指定身份，拒绝把普通哈希签名误报为固定身份。

`check-signing-identity.sh`只复制现有应用并操作离线副本，不启动应用、不请求权限、不访问音频或HID。实际通过五组检查：旧哈希拒绝新版本；不同代码哈希在写入来源信息并重签后使用同一显式身份；无效模式与证书冲突在签名前拒绝；其他应用标识拒绝；修改密封内容但不重签时拒绝。路径包含空格的副本也通过。副本检查结束自动移除。

## 第二阶段：Cask最终签名接入

0.2.14开发源码的`build-cask.sh`开启固定身份模式；来源标记增加`signingPolicy=identifier-only-adhoc-v1`，写入后仍通过统一入口签名。构建与安装核验读取声明并核对最终要求；旧版没有字段时明确报告旧版检查，不将旧版严格签名有效说成固定身份已验证。`make check`增加上述离线检查，后续CI会运行同一路径。

实际在本地用合成来源参数运行完整Cask前置脚本，通过105/105核心、109/109适配器、独立CLT Release编译、Mach-O macOS14/SDK27检查、0.2.14版本与应用自检。初次与来源标记后的最终签名均核验为固定身份；仅检查该本地构建，没有将合成来源参数写入安装版，也没有从本地归档安装。

以该最终Cask构建为基础再运行离线检查，五组全部通过，包括把已采用固定身份的副本重新切回默认哈希模式作为对照。`make homebrew`的本地归档及渲染后Cask的Ruby语法通过；这只是打包预览，不作为远端安装成功的证据。

新版安装核验脚本对现有0.2.13执行只读兼容检查，通过来源、严格签名、CLI、自检、唯一app和构建缓存检查，并明确提示旧版没有固定身份声明。安装版、其授权和设置均未改动。源码与文档按阶段提交；用户随后明确授权发布与保留配置的远端升级，执行记录见下节。

## 待验收

真实系统授权能否在采用该规则的两个版本间保留、从远端Cask升级的集成结果及最低macOS/Intel结果尚未验证。源代码与签名规则检查不能代替这些验收，也不提供Gatekeeper批准。

发布后按README从公开HTTPS源码升级并保留配置；由用户完成首次迁移授权，再在代码哈希变化但规则不变的下一次远端源码升级后，检查实际TCC要求及原生API状态。只有该流程通过，才可报告本机授权保留；其他macOS版本仍单列。已有语音胶囊单屏验收与跨屏跳过状态保持不变，不在本次签名试验中补记通过。
