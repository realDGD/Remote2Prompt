# 无证书固定身份的源码构建试验

日期：2026-10-29。用户要求先核实普通升级是否失去权限，随后明确选择尝试无证书的固定身份规则。只修改本项目构建与验证，不重置TCC、清隔离标记、创建证书或修改系统安全设置。

## 已确认的故障

本机Homebrew日志记录0.2.12到0.2.13的普通升级，配置数据及向导标记在新应用首次启动前保持一致。紧接升级后的TCC系统日志对输入监控及设备控制明确报告`Failed to match existing code requirement`，旧、新代码哈希不同。后续系统记录已更新为新版授权，原生权限页也显示允许；这不否定升级时的实际失配。

Homebrew的`signer changed`提示属于启动隔离批准继承逻辑，本身不能证明TCC授权失效。本次故障结论依据实际TCC日志，原始诊断只保留在忽略目录，不上传。

## 第一阶段：统一签名入口

`build-app.sh`使用统一的`sign-app.sh`，保留本地默认代码哈希与显式固定身份两种模式；已有证书入口保持可用，不创建证书。`verify-signing-identity.sh`同时检查严格签名有效性和指定身份，拒绝把普通哈希签名误报为固定身份。

`check-signing-identity.sh`只复制现有应用并操作离线副本，不启动应用、不请求权限、不访问音频或HID。实际通过五组检查：旧哈希拒绝新版本；不同代码哈希在写入来源信息并重签后使用同一显式身份；无效模式与证书冲突在签名前拒绝；其他应用标识拒绝；修改密封内容但不重签时拒绝。路径包含空格的副本也通过。副本检查结束自动移除。

真实系统授权能否在采用该规则的两个版本间保留、从远端Cask升级的集成结果及最低macOS/Intel结果尚未验证。源代码与签名规则检查不能代替这些验收，也不提供Gatekeeper批准。
