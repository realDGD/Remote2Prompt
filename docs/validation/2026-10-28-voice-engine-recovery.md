# 语音中断与回环输出修复

## 现场与复现

用户报告语音开始可用，随后无法唤起微信语音，重新连接音频后暂时恢复；截图显示物理语音键仍按下，合成右 Control 已松开。实际设备状态为“音频队列已满，语音会话已停止”，后续按下却显示泛化的语音开关/连接/权限提示。不能把最初一个“正在按住”快照当作持续丢失松开事件；用户和后续 UI 均确认后来显示了松开。

退出安装版、保留配置后，用独立 CLT 探针运行实际 LoopbackWriter，仅输出静音，不记录声音、HID 或硬件标识：

- 原实现不切默认输入：500 批共 80000 样本连续播放并排空通过，默认输入/输出未变。
- 原实现播放中切到虚拟输入：引擎由 running 变为 stopped，播放器仍 playing，pending 持续增长；约 4.2 秒、421 批后溢出，结束时默认输入/输出恢复。
- “重新启动同一引擎”的第一候选短测曾通过，但正式主执行器测试及与应用一致的 SDK 链接测试仍溢出。诊断还观察到系统输入变化后输出绑定改变，重新绑定后 running 为 true 仍不能证明在消费数据。该方案未发布。

输入切换导致输出中断是本机已复现路径，不将其扩展为所有蓝牙、所有驱动的唯一原因。

## 修复与已执行检查

使用独立 Audio Queue，按 UID 直接绑定所选虚拟设备，替代依赖默认输入/输出图的 AVAudioEngine。缓冲消费仅回收容量，最终还须确认异步停止已完成才报告排空。失败仍释放触发键并恢复输入；不会为了保持“按住”忽略音频失败。后续按下保留具体错误，输出失效使未完成的配置回调过期。决策见[Agent Note](../../.agents/notes/implemented/bug-fix/2026-10-28-loopback-device-queue.md)。

- `make test`：核心 69/69、macOS 适配器 70/70 通过。新增 11 项使用真实队列所有者和模拟后端，覆盖消费/播放结束区别、排空失败与旧排空回调、路由通知隔离、配置失败、取消后旧缓冲、容量回收及 32000 样本上限；不访问设备或发送系统按键。
- 正式 `VoiRemoteMacChecks --loopback-stream-smoke --switch-input`：使用与应用一致的 macOS 14 最低版本和实际 CLT SDK 27 链接，同一输出连续三次会话，共 384000 静音样本；每次播放中切为虚拟输入再恢复原输入，全部排空通过，未溢出，最后默认输入/输出与测试前相同。
- CLT Release 构建和 `verify-app.sh`：本地 0.2.4 应用包通过，Mach-O 最低 macOS 14、SDK 27 与实际工具链匹配，临时签名与配置自检通过。

硬件入口默认不切系统输入，只有显式 `--switch-input` 才临时切换；要求退出实际应用且仅有一个兼容回环设备，错误路径也等待清理并校验恢复。测试期间若外部选择另一个设备，不覆盖该选择。普通 `make test` 和 CI 不执行此硬件入口。

## 输入接管与竞态补验

用户追加要求核对真实系统默认输入与竞态。显式 `--voice-input-session-smoke` 使用生产 `AudioInputPriorityRuntime`、`InputPriorityCoordinator`、`CoreAudioInputSystem` 及 Audio Queue，模拟语音边界并输出静音：

- 空闲 ready 不切输入；每轮按下均等待读回确认虚拟输入后才开始输出。
- 三轮按下/排空/结束均恢复到测试前精确原 UID；第一轮按住时显式模拟一次实体输入抢占，运行时重新选回虚拟输入，未改写恢复基线。
- listener 全部清理，默认输出未变；未捕获声音或向输入法发送触发键。CLI 中显式刷新替代 AppKit 定时器，这不是 HID 或微信端到端测试。

检查还发现调用顺序风险：音频 readiness 的发布、权限变化和停止/退出路径可先降低输入 ready，从而在触发键释放前恢复原麦克风；按住时修改输入切换开关也未先取消音频。补丁统一在降低 ready 之前取消活动音频，沿用 onEnd 的“释放键 → 结束输入事务”顺序；开关变化先停止旧会话。这些顺序问题由源码调用链确认与修正，未通过物理断蓝牙/撤销权限实测。

新增四项实际输入运行时配合模拟系统的回归：旧接管待确认时快速重按、旧恢复待确认时重按、ready 恢复不能自行重开语音、待确认期间关闭再打开输入优先。核心 69/69、适配器 74/74 通过；它们不写真实系统输入，也不等同上述映射运行时回调顺序的硬件验证。

已覆盖的保护还包括旧会话/路由代次隔离、松开早于确认、晚到写入与新系统选择、写前检查来源、最多三次失败及有限排空。CoreAudio 不提供原子比较并写入，超过确认窗才执行的驱动请求和强制结束仍有明确边界，不能声称消除了所有竞态。

## 真实长按仍失声与时间线补验

0.2.5 实际远端安装与来源、签名、单份 app、缓存清理检查通过；配置数据保持一致。更新后用户重新关联设备控制授权，界面确认设备控制和监听均允许。RC003 随后已被枚举，实际语音时界面显示接收中，默认输入为 MiRemoteV；结束后恢复原输入。

但用户明确报告：持续按住时，微信仍显示录音，声音开始可用、几秒后消失；把微信麦克风从自动检测固定为 MiRemoteV 仍失声。因此 **0.2.5 未通过真实持续语音验收**，不能据静音排空或 CI 通过宣称语音故障解决。

独立突发探针按 120 ms 批次供应 PCM，并插入 300 ms 到包间隙。原时间线下缓冲的实际排队起点逐渐落到播放时钟之前；960 批时，排队起点约 230160、播放时钟约 259518 帧，尽管 running 和 drain 仍通过。重设时序候选在同一探针中恢复到时钟之后，未溢出。这是已复现的时间线错误，但尚不能证明它是实际失声的全部原因。

0.2.6 候选在欠载时 Flush 转换器并为新缓冲指定时钟之后 50 ms 的起点，不重置已排队音频。四项纯时钟回归覆盖连续播放、欠载、会话重置和无效时钟；计数回归拒绝旧会话回调。新增收包、解码、提交、消费、待输出、最近到包、信号变化、播放进度和时序恢复诊断，仅内存保留，每两秒刷新，不保存音频或原始数据包。候选的核心 73/73、适配器 75/75、CLT Release 与 bundle 校验通过；实际 `--switch-input --jitter` 三轮共 384000 静音样本排空通过，发生时序恢复且迟到缓冲为零，默认输入/输出恢复。真实长按仍须更新后借助诊断复验。
