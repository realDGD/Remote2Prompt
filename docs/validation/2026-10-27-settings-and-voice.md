## 输入监控排查

沿用此前已经取得的负例：公开 IOHIDRequestAccess 与 CGRequestListenEventAccess 返回拒绝；仅重置本应用 ListenEvent 后，人工与自动化点击均未看到系统框或自动加入列表。无线麦采用相同请求 API；签名身份漂移能解释重编译后的授权失配，不能据此断言是未弹框的全部原因。

本轮改为 IORegistry 元数据发现，避免启动阶段通过 HID Manager 创建 plug-in/user client；该风险由 Apple IOKitUser 源码路径核查得到，**尚未证明这就是弹窗根因**。同步 TCC 检查和请求移到串行后台队列，状态不变时不持续发布，避免主线程阻塞及反复重建界面。原生 API 仍由用户操作触发，无自建授权替代框。

按用户允许的后备方式，设置入口提供非模态拖入引导：打开真实输入监控设置，以当前 bundle URL 的 NSDraggingItem 提供 app 图标和箭头，用户自己拖入并打开开关。面板显式写明这是应用操作帮助，不伪装系统授权，不自动授予权限。

本轮 Computer Use 的 getApp 对当前应用与系统设置都连续超时，虽然应用自身 CLI UI smoke 成功。未能用该工具复测最终构建的真实系统弹窗、系统设置跳转、鼠标拖放或快捷键确认/取消交互，也没有借此扩大重置范围、重启 tccd 或改隐私数据库。当前系统弹窗仍记为未修复验证。
